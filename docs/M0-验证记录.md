## 集成中发现并修复的两个静默 bug

类型检查和单模块测试都抓不到，只有实测才暴露。

### 1. 屏幕震动被缩小 57 倍（等于没有）

`feelConfig.shake.maxPitch/maxYaw/maxRoll` 写的是**度**，`TraumaShake.update()`
内部已经乘过 `π/180` 输出**弧度**；而 `Player.applyCameraOffsets()` 按注释假设
入参是度，又乘了一次 `DEG`。

结果：M0 最核心的那一层反馈被静默地缩小到 1/57。类型正确、无报错、无警告。

**修复**：`player.ts` 去掉二次转换，并在注释里写死单位约定。

### 2. 枪模弹簧在一次卡顿后永久发散

`viewmodel.ts` 的 `updateKick` 用显式欧拉积分开火脉冲弹簧
（`KICK_STIFFNESS=300`、`KICK_DAMPING=24`）。该积分器的稳定上限约
`dt < 2/KICK_DAMPING ≈ 0.083s`，而 `core/time.ts` 的 `MAX_FRAME_DT` 钳位是 **0.1s**。

只要出现一次超过 83ms 的帧（切标签页、GC、着色器编译、断点），弹簧就发散，
且因为是自激的**永远回不来**：实测 `viewModel` 根节点 `position.z` 达到
`2.1e+24`，`muzzleWorld` 跟着变成天文数字，曳光弹和枪口火光全部失效。

**修复**：改为 1/240s 定长子步进（保住原有刚度/阻尼手感，任意帧时长下无条件稳定）
+ 非有限值兜底清零。

> 全项目扫描确认只有这一处手写积分器，其余全部用 `expApproach`（无条件稳定）。
> 契约里「帧率无关插值统一走 expApproach」这条纪律挡住了其余 7 个模块。

## 关卡光照：实测标定

原始值（`hemi 0.34 / ambient 0.28 / sun 0.55 / lamp 22 / window 9 / fire 14`）
在 1280×720 下实测**整屏平均亮度只有 2.4/255，可见像素（lum>24）0.3%** —— 一片漆黑。
这是"破的暗"，不是"艺术的暗"。

在浏览器里做参数扫描（8px 网格采样 + 分位数统计），最终标定值：

| 灯 | 原值 | 标定值 |
|---|---|---|
| `alley-hemi` | 0.34 | **8.2** |
| `alley-ambient` | 0.28 | **4.2** |
| `alley-sun` | 0.55 | **9.9** |
| `alley-lamp` | 22 | **220** |
| `alley-window` | 9 | **90** |
| `alley-fire` | 14 | **140** |

标定后的亮度分布：

| 机位 | 平均亮度 | 中位数 | p90 | 可见像素 | 过曝 |
|---|---|---|---|---|---|
| 出生端 z=18 | 36.3 | 17 | 83 | 47% | 0% |
| 中段 z=-6 | 54.7 | 34 | 116 | 67% | 0.8% |
| 远端 z=-19 | 32.5 | 38 | 54 | 56% | 0% |

选型理由：同时试过"抬环境光"和"抬点光源"两个方向。均匀抬环境光能到同样的平均
亮度，但会抹掉「暗巷里唯一的亮处」的戏剧性（p90/p50 对比度从 4.6 掉到 2.8）。
最终取的是中间档：基调灯抬到能读出墙面材质，暖色光池仍然明显突出。

## 其他修复

- **开始界面就被打**：出生点有视线的 1 号敌人在 gate 未点击时就已开火，玩家进游戏前
  已掉到 91 血。加 `started` 门控，点击开始才激活敌人 AI 并重置全场。
- **draw call 统计恒为 1**：postprocessing 一帧 render 多次，`renderer.info.autoReset`
  让统计只反映最后一个全屏 pass。改为手动每帧 `reset()` 一次。
- **rAF 停摆**：浏览器在窗口不可见时暂停 `requestAnimationFrame`，循环整个冻死。
  改成 rAF 与 setTimeout 竞速、`gen` 计数作废慢的那个 —— 无状态机自愈。

# 性能诊断（2026-07-27 · 用户反馈「太卡」）

## 结论先行

卡的原因**不是** GPU、不是分辨率、不是粒子、不是贴花、不是音频，
而是 **three.js 的 shader program 会随「场景中可见灯光的数量」重新编译**。

`LightPool` 的 4 盏动态点光源平时 `visible = false`，开枪时才点亮。
每点亮一盏，场景点光源数就从 3 变成 4、5、6 —— **整个场景所有受光材质
全部按新的灯光数重编 shader**。实测：

- 第 1 枪点亮第 1 盏 → 重编 12 个 program → **冻结 349ms**
- 第 2 枪再亮一盏 → 又 12 个 → **冻结 403ms**
- 第一次打中金属（弹着火花额外要一盏灯）→ **冻结 1233ms**

正好全砸在最需要打击感的头几枪上。

**修复**：池里的灯常驻 `visible = true`，闲置时 `intensity = 0`。
intensity 为 0 的灯对画面零贡献，但能让灯光数恒定，一次都不用重编。

| 怀疑项 | 实测 | 判定 |

| 贴花池打满 | 无明显影响 | 排除 |
| 分层音频 | 枪声 0.833ms + 弹着 0.425ms，700RPM 下约占 60fps 预算的 1.5% | 排除 |

## 顺带修掉的三件事

1. **帧调度器把游戏锁在 16 FPS**。上一轮为了在无窗口环境下做验证，加了
   固定 `setTimeout(run, 60)` 兜底。浏览器一旦节流 rAF（窗口不在前台/被遮挡），
   它就以 60ms 为周期驱动 —— 一帧只要 2.5ms 的游戏被压成 16 FPS。
   改成自适应：rAF 正常时兜底设 150ms（纯空转），真停摆才收紧到 8ms。
   HUD 的 stats 行现在会显示当前驱动来源（`rAF` / `⚠兜底`）。

2. **鼠标输入没有按帧合并**。原来每个 `mousemove` 事件都立刻调 `player.look()`；
   游戏鼠标 1000Hz 轮询时一帧内来十几个事件，转向被拆成多次微小更新。
   改成攒在帧里一次性应用。

3. **着色器惰性编译**。加了迭代式预热（在开始界面阻塞编译，直到 program 数
   连续两轮不再增长）。灯光数修复后，需要预热的变体从 71 降到 34，
   预热耗时也大幅下降。

## 留下的工具

- `__bs.profile(seconds)` —— 在**真实 rAF 循环里**采样每个子系统的分段耗时。
  排查卡顿时先用它，不要把子系统拎出来单独测（会漏掉相互作用，我就栽过一次）。
- HUD stats 行：`FPS · 帧耗时 · 驱动来源 · 粒子 · draw call · 三角形 · 贴花`。
  **帧耗时和 FPS 必须一起看** —— 帧耗时 2.5ms 却只有 16 FPS，瓶颈就一定在调度而非渲染。
- **F 键**切三档画质预设（实测在 RTX 5060 上三档差异很小，因为本作不是 GPU 受限；
  它是给弱机器的保险，不是这次卡顿的解法）。

## 给后续开发的两条规则

1. **不要用 `light.visible` 开关灯**。要熄灭就把 `intensity` 设为 0。
   任何改变场景可见灯光数量的操作都会触发全场材质重编译。
2. **不要在战斗中首次引入新的材质/几何属性组合**。所有会在战斗里出现的
   shader 变体，都必须在 `warmUp()` 里先走一遍。

## 已知取舍

- **未用 three.quarks**：M0 只有 3 个特效，自写 InstancedMesh 粒子池（零 API 风险、
  完全控制）比接一个未验证的库更稳。M3 特效大量铺开、需要 quarks.art 可视化编辑器
  工作流时再接。
- **未用 bitECS**：M0 实体类型只有 3 种，ECS 的收益在实体规模上来后才显现。
  但状态和行为已经分离，M1 迁移成本低。
- **敌人命中判定简化**：敌人开枪只做朝向玩家的窄锥点积判定，不做完整射线。
  M0 是打靶场，重点是验证玩家侧的手感。
